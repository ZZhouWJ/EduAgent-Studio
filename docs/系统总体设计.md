# EduAgent Studio 系统总体设计

> 项目：智学工坊 EduAgent Studio
>
> 赛题：A3 基于大模型的个性化资源生成与学习多智能体系统开发
>
> 设计基线：V2.1，2026-07-17

## 1. 系统定位

EduAgent Studio 面向高校课程教与学场景，将课程知识、学生画像、多智能体资源生成、AI 辅导、教师审核和学习反馈放在同一条可追溯链路中。

首个完整课程场景为《数据库系统原理》（CS301），系统设计本身支持通过课程、知识点和材料数据扩展到其他学科。

## 2. 设计目标

| 目标 | 验收方式 |
| --- | --- |
| 学生画像真实可更新 | 自然语言抽取后由学生确认，回写画像与更新历史 |
| 资源生成体现多智能体协作 | 可见诊断、规划、生成、评测、审核和返工轨迹 |
| 个性化不只是 Prompt 文案 | 画像、掌握度、任务和反馈同时参与路径、推荐和生成 |
| AI 内容可信 | 引用真实课程 chunk，校验证据 ID，没有证据时降级为草稿 |
| 教师保留教学决策权 | 所有学生可见资源必须经教师审核通过 |
| 平台可治理 | 用户、模型、Prompt、调用、成本、风险和日志均可管理 |
| 工程可复现 | Docker Compose、迁移链、健康检查和自动化测试可验证 |

## 3. 角色与用例

### 3.1 学生

- 通过 Tutor 主入口进行课程问答，查看工具进度、引用和多模态内容块。
- 通过对话描述目标、基础、时间与偏好，确认抽取结果后更新画像。
- 按掌握度和先修关系查看个性化学习路径。
- 开始、完成教师任务，学习已审核资源。
- 提交测验、掌握度自评、疑问和资源评价，查看学习报告。

### 3.2 教师

- 管理自己的课程、学生、知识点和学习任务。
- 上传 PDF、DOCX、PPTX 和文本课程材料，解析、检索、重解析并确认知识点关联。
- 在工作台选择学生、知识点、难度、目标和资源类型，执行多智能体生成。
- 核验内容、证据、难度和教学建议，通过或退回资源。
- 查看掌握度、薄弱点、任务进度、反馈和资源质量。

### 3.3 管理员

- 管理用户、角色、账号状态和课程教师归属。
- 管理模型供应商、加密凭证、模型实例、智能体能力和 Prompt 版本。
- 查看调用、Token、成本、登录、操作和资源审核日志。
- 管理内容安全、引用覆盖率、小时调用上限、月度预算和告警阈值。

## 4. 领域模块

| 模块 | 主要输入 | 主要输出 |
| --- | --- | --- |
| 认证与权限 | 用户名、密码、JWT、角色、课程归属 | 可撤销会话、用户上下文、数据域判定 |
| 课程与知识库 | 课程、知识点、材料文件 | 可检索 chunk、知识点关联、引用证据 |
| 学生画像 | 对话、反馈、测验、自评 | 12 维特征、掌握度、更新历史 |
| 学习规划 | 画像、知识点、掌握度、学习目标 | 有顺序的路径节点、时长和资源建议 |
| 多智能体资源生成 | 学生、知识点、难度、类型、目标 | 资源草稿、评测、审核建议、证据与轨迹 |
| Tutor 辅导 | 学生问题、课程、画像、附件 | 回答、引用、工具轨迹、内容块与会话历史 |
| 任务与反馈 | 教师任务、学生进度、测验和自评 | 任务状态、掌握度更新、推荐调整 |
| 审核与治理 | 资源、证据、模型调用、策略阈值 | 审核结论、风险拦截、成本和审计记录 |

## 5. 核心业务流

### 5.1 画像构建

```text
学生发送自然语言描述
  → 存储 user message
  → LLM 抽取结构化画像候选
  → 存储 assistant message + extracted_json
  → 学生检查并确认
  → 事务内更新画像、标记消息已应用、写更新历史
```

抽取失败时保留对话但不自动覆盖画像。多值维度在写入前归一化并去重。

### 5.2 多智能体资源生成

```text
教师发起生成
  → 校验教师课程归属、学生归属和知识点归属
  → 读取画像、掌握度、学习历史和课程证据
  → LangGraph 执行诊断/规划/生成/评测/审核/返工
  → SSE 推送节点进度
  → 教师检查最终结果
  → 事务内保存草稿与证据链
```

工作流使用 SQLite checkpoint 持久化，同一 `run_id` 可在进程重启后查询。

### 5.3 资源审核

```text
draft/rejected
  → 教师提交审核
pending_review
  ├─ approved：通过，学生可在资源库与推荐中看到
  └─ rejected：退回，必须记录理由，修改后可重新提交
```

通过时若存在高风险审核标记，服务拒绝将资源标记为 `approved`。

### 5.4 任务与反馈闭环

```text
教师创建任务（draft）
  → 分配学生（assigned）
  → 学生开始（in_progress）
  → 学生完成（completed）
  → 提交测验/自评/疑问/资源评价
  → 更新知识点掌握度和画像历史
  → 重新计算学习路径与推荐
```

学生进度保存在 `learning_task_progress`，不会因一名学生完成而改变其他学生的状态。

## 6. 数据模型

### 6.1 主要关系

```text
users
  ├─ user_roles → roles → role_permissions → permissions
  ├─ auth_sessions
  ├─ student_profiles → student_knowledge_mastery
  └─ tutor_sessions → tutor_messages

courses
  ├─ knowledge_points
  ├─ course_materials → course_material_chunks
  │                         └─ kp_chunk_links ← knowledge_points
  ├─ learning_tasks → learning_task_progress
  ├─ learning_resources → learning_resource_reviews
  │                        └─ resource_evidence_links → course_material_chunks
  └─ learning_feedbacks
```

### 6.2 数据所有权

| 对象 | 学生 | 教师 | 管理员 |
| --- | --- | --- | --- |
| 学生画像 | 读写自己 | 读授课课程学生 | 按治理需要读 |
| 课程材料 | 不管理 | 管理自己课程 | 管理全平台 |
| 资源 | 只读 approved 且可见课程 | 生成/审核自己课程 | 读取与治理 |
| 任务进度 | 更新自己 | 查看授课课程汇总 | 平台分析 |
| Tutor 会话 | 读写自己 | 不直接读私人会话 | 不通过常规页面读正文 |
| 模型凭证 | 无权限 | 无权限 | 可写入，不回显明文 |

## 7. API 设计

- 业务 API 使用 `/api` 前缀，统一返回 `code` / `message` / `data`。
- 分页接口显式返回总数、页码和每页条数。
- 无权访问与资源不存在使用一致的 HTTP 状态与业务错误。
- 文件上传使用 multipart，下载使用经过所有权校验的存储端点。
- 多智能体和 Tutor 使用 SSE 返回结构化事件，最终事件包含完整结果。
- 生产环境关闭 Swagger/Redoc，开发环境可用于契约检查。

## 8. 非功能设计

### 8.1 安全

- 密码 BCrypt 哈希，JWT 密钥与 API Key 加密密钥分离。
- 生产启动时强制检查随机密钥、明确 CORS 和非 Mock 模型。
- Repository 使用参数化 SQL，上传文件使用安全文件名、类型和容量限制。
- Markdown/HTML 渲染前消毒，LLM 输入、输出和工具参数经内容安全扫描。

### 8.2 可用性与可恢复性

- API、MySQL、Redis 和 Frontend 分别暴露健康检查。
- Docker Compose 通过健康依赖控制启动顺序。
- MySQL、Redis、课程文件和 checkpoint 使用持久卷。
- 多智能体步骤状态存入 SQLite checkpoint，流式连接中断不等于丢失已完成状态。

### 8.3 性能

- 前端页面按路由懒加载，复杂图表按页面进入时加载。
- 列表和日志使用服务端分页，课程数据域在 SQL 查询阶段过滤。
- 课程文档按 chunk 检索，只将最相关证据注入 Prompt。
- 计算成本较高的长时任务可通过 Celery 与 Web 请求分离。

### 8.4 可访问性与响应式

- 三角色路由支持 390px 移动视口和 1440px 桌面视口。
- 图标按钮具有可读名称，复合控件使用 Radix 键盘/ARIA 基础。
- 表格、图谱和长代码在小屏内局部滚动，不使页面整体横向溢出。
- 动效尊重 reduced-motion 偏好，加载、空状态、错误和重试都有明确交互。

## 9. 当前外部边界

- 讯飞星火、图像、TTS 和 ChatDoc 的调用代码已实现，但真实竞赛验收依赖项目负责人配置有效凭证与开通的服务权限。
- 系统不将 Mock Provider 输出当作真实讯飞证据。
- 最终演示视频、最新 DOCX 和 PPTX 需以当前代码、截图与测试基线生成。

## 10. 验证与变更控制

1. 功能修改必须有针对性测试，交付前执行后端全量测试、前端类型检查和生产构建。
2. 新增 API 必须同时定义请求模型、权限、所有权、错误分支和前端类型。
3. 新增 AI 能力必须说明 Provider 降级、内容安全、证据、审核和成本记录。
4. 数据模型修改通过顺序 SQL 迁移完成，同步 Compose 挂载、迁移清单测试和数据库文档。
5. 实测基线以 `docs/PROJECT_STATUS.md` 和 `docs/测试说明书.md` 为准，不以历史阶段计划判定完成状态。
