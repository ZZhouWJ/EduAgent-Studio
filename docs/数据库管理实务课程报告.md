# 《智研协作 AI 项目质量审计系统》数据库管理实务课程报告

## 摘要

本课程报告围绕“智研协作 AI 项目质量审计系统”的设计与实现展开。系统面向高校项目协作场景，针对 AI 生成内容难追踪、多人协作版本混乱、审核记录分散、成果沉淀不清晰、模型调用成本不可见等问题，构建了一个基于 MySQL 数据库、FastAPI 后端和 Vue3 前端的 Web 前后端分离信息管理系统。系统功能覆盖注册登录、用户权限、项目空间、任务与版本管理、AI 生成、提示词模板、模型管理、输出编辑、批注协作、审核评分、成果采用、分支合并、调用审计、成本统计、操作日志和统计看板等模块。

数据库层采用 MySQL 8.0，库名为 `ai_collab_audit_system`，核心业务表共 27 张，并设计了主键、外键、唯一约束、索引、软删除字段、审计字段、视图、触发器和存储过程。后端采用 FastAPI 分层实现，使用 Router、Service、Repository 结构组织业务逻辑，通过参数化 SQL 完成数据访问，不使用 ORM 替代核心 SQL。前端基于 V3 Admin Vite 开源 Vue3 后台模板二次开发，使用 Vue3、Vite、TypeScript、Element Plus、Pinia 和 Vue Router 构建交互界面。

本系统不仅满足数据库管理实务课程对“完整、可运行的信息管理系统”的要求，也体现了数据库设计、事务处理、并发控制、审计日志、统计查询和前后端联调等综合实践能力。当前项目代码与文档已完成静态核对，涉及数据库导入、前后端完整联调与截图的内容仍需在本地 Windows MySQL + Node 环境中补充验证。

**关键词**：数据库管理实务；MySQL；FastAPI；Vue3；AI 协作；版本管理；质量审核；成果库；统计看板

## 一、需求分析

### 1.1 系统开发背景

在高校课程设计、毕业设计和团队项目中，AI 工具能够快速生成需求分析、数据库设计、代码片段、报告章节和测试素材，提高项目初稿产出效率。但 AI 参与后也带来新的管理问题：多人协作过程难以追踪，AI 生成内容质量不可控，不同版本输出容易混乱，审核过程缺少结构化记录，最终成果难以沉淀，模型调用成本和质量表现缺少统计依据。

传统项目管理工具通常更关注任务分配和进度管理，对 AI 生成内容的版本链、人工修改过程、审核评分、问题标签和成果采用记录支持不足。因此，本项目选择“高校项目协作 + AI 任务生成 + 质量审计”作为数据库课程设计场景，通过关系型数据库记录项目全过程数据，形成可追踪、可审核、可统计的协作管理系统。

### 1.2 用户角色分析

系统角色分为全局系统角色和项目内角色。系统管理员负责用户管理、角色权限、模型管理、API 配置、日志查看和全局统计；普通成员通常参与项目任务、AI 生成、输出编辑和批注协作；项目负责人在具体项目内承担 `leader` 角色，可管理项目成员、任务、成果采用和分支合并；审核人员在项目内承担 `reviewer` 角色或被指定为审核人，负责审核输出内容；指导教师在项目内承担 `teacher` 角色，可参与指导、审核和成果确认。

需要特别说明的是，教师和学生身份并不直接等同于某个项目的权限。项目级权限以 `project_members.project_role` 为准，取值包括 `member`、`leader`、`reviewer`、`teacher`。例如，学生可以是某项目的负责人，教师也可能只在某项目中担任审核人员或普通成员。

### 1.3 功能需求

系统功能模块包括：注册与登录、用户与权限管理、项目空间、任务与版本管理、AI 生成、提示词模板、模型管理、输出编辑与批注、审核中心、成果库、分支合并、调用审计、成本统计、操作日志、登录日志和统计看板。

注册与登录模块支持用户注册、登录、获取当前用户、退出登录和修改密码。用户与权限模块支持用户列表、启用禁用、角色分配和权限查询。项目空间模块支持项目创建、列表、详情、成员管理、任务列表和项目统计。任务与版本模块支持任务创建、分支管理、输出版本列表、输出详情、版本时间线和另存为新版本。AI 生成模块支持模型选择、提示词版本选择、输入文本、Mock 模型调用和生成结果入库。审核中心支持提交审核、待审核列表、审核详情、评分和问题标签。成果库支持成果采用、成果列表、成果详情和 Markdown 导出。统计模块支持项目统计、模型调用统计、成本统计、审核质量统计、成员贡献排行和最近操作动态。

### 1.4 数据需求

系统需要管理的数据对象包括用户、角色、权限、用户角色关系、角色权限关系、项目、项目成员、任务类型、项目任务、任务分支、输出版本、提示词模板、提示词版本、模型供应商、AI 模型、API 配置、模型调用记录、成本记录、批注、审核请求、审核记录、问题标签、输出问题关联、采用成果、分支合并记录、操作日志和登录日志。

这些数据对象之间存在明确关系：用户通过项目成员关系参与项目；项目包含任务；任务包含分支和输出版本；输出版本可以来自 AI 调用或人工编辑；输出版本可以被批注、提交审核、形成审核记录、关联问题标签，并在审核通过后被采用为成果；模型调用记录与成本记录为统计看板提供数据基础。

### 1.5 非功能需求

系统需要满足安全性、数据一致性、可维护性、可扩展性、易用性、可审计性和并发修改控制等要求。安全性方面，密码必须哈希存储，JWT 用于身份认证，API Key 需要加密保存并脱敏展示；数据一致性方面，多表写入需要事务保护；可维护性方面，后端采用 Router、Service、Repository 分层结构；可扩展性方面，Mock ModelAdapter 可后续替换为真实模型 API；可审计性方面，系统记录登录日志、操作日志、模型调用记录和成本记录；并发控制方面，输出编辑使用 `lock_version` 乐观锁。

## 二、系统设计与技术实现

### 2.1 系统总体架构

系统采用 Web 前后端分离架构。前端基于 V3 Admin Vite 二次开发，使用 Vue3、Vite、TypeScript、Element Plus、Pinia、Vue Router 和 ECharts；后端基于 FastAPI，负责认证、业务接口、统一响应、异常处理和数据库访问；数据库采用 MySQL 8.0；数据库访问使用参数化 SQL 和 Repository 层；AI 调用层当前采用 Mock ModelAdapter，可扩展为真实模型 API；审计层通过 `operation_logs`、`login_logs`、`ai_invocations`、`cost_records` 等表记录系统行为。

### 2.5 数据库物理结构与约束设计

数据库物理设计以 `database/02_create_tables.sql` 和 `database/03_create_indexes.sql` 为依据。系统所有主表均使用自增整数主键，例如 `users.user_id`、`projects.project_id`、`project_tasks.task_id`、`task_outputs.output_id`、`review_requests.request_id`、`output_reviews.review_id`、`adopted_outputs.adopted_id`。外键用于维护实体间关系，例如任务关联项目，输出版本关联任务，审核请求关联输出版本，成果记录关联输出版本。

系统设计了多种唯一约束，例如 `users.username`、`users.student_no`、`users.email`、`roles.role_code`、`permissions.permission_code`、`project_members(project_id, user_id, is_deleted)`、`prompt_versions(template_id, version_no)`、`ai_models(provider_id, model_name, is_deleted)`。这些约束用于避免账号、角色代码、权限代码、项目成员和版本号重复。

核心业务表普遍设置非空约束、默认值、软删除字段和审计字段。软删除字段包括 `is_deleted`、`deleted_at`、`deleted_by`；审计字段包括 `created_at`、`created_by`、`updated_at`、`updated_by`。状态字段通过数据库枚举或业务校验保持合法，例如输出状态包括 `draft`、`generated`、`submitted`、`approved`、`rejected`、`revision_required`、`adopted`、`conflict_pending`。索引脚本为用户、项目、任务、输出、审核、调用和日志查询建立二级索引，以提升检索和统计性能。

### 2.6 数据库高级特性实现

系统设计了 5 个视图：`v_project_task_statistics`、`v_model_invocation_statistics`、`v_pending_reviews`、`v_user_permissions`、`v_artifacts`。这些视图用于封装项目任务统计、模型调用统计、待审核列表、用户权限查询和成果库查询。

系统设计了 5 个存储过程：`sp_archive_project`、`sp_create_project_with_owner`、`sp_submit_output_for_review`、`sp_complete_review`、`sp_adopt_output`。其中 `sp_archive_project` 用于归档项目并处理关联任务和分支状态；`sp_create_project_with_owner` 用于创建项目并绑定负责人；`sp_submit_output_for_review` 和 `sp_complete_review` 用于审核流程；`sp_adopt_output` 用于成果采用。

系统还设计了 3 个审核相关触发器：`trg_output_review_approved`、`trg_output_review_rejected`、`trg_output_review_revision_required`，用于辅助审核状态变化后的自动处理。

事务方面，后端在注册、创建项目、创建任务、输出编辑、审核完成、成果采用和分支合并等多表写入场景使用事务，保证业务数据和 `operation_logs` 一致写入。乐观锁方面，输出编辑接口要求携带 `lock_version`，更新条件同时匹配 `output_id`、`lock_version` 和 `is_deleted = 0`，若 affected_rows 为 0，则返回并发冲突错误。参数化 SQL 方面，后端 Repository 层统一使用 `%s` 占位符传参，避免拼接用户输入。

### 2.7 后端系统实现

后端基于 FastAPI，主要目录包括 `routers`、`services`、`repositories`、`utils`、`adapters`、`config.py`、`database.py` 和 `main.py`。`routers` 层负责声明接口路径和请求模型，`services` 层负责业务流程和权限判断，`repositories` 层集中编写参数化 SQL，`database.py` 负责数据库连接和事务上下文，`utils/response.py` 提供统一响应格式，`utils/exceptions.py` 提供基础异常处理。

后端主要接口模块包括 auth、users、projects、tasks、prompts、models、invocations、reviews、artifacts、statistics 和 logs。统一成功响应格式为 `{"code":0,"message":"success","data":...}`，错误响应使用非 0 业务码并返回错误信息。认证模块使用 JWT，密码通过哈希校验，API Key 通过 AES-GCM 加密保存并仅展示脱敏 `key_mask`。

### 2.8 前端系统实现

前端基于 V3 Admin Vite 开源模板二次开发，保留开源来源与许可证说明，并清理原模板 Apifox Mock API 和无关演示页面。前端使用 Vue3、Vite、TypeScript、Element Plus、Pinia、Vue Router 和 ECharts，页面包括登录、注册、Dashboard、项目空间、项目详情、任务列表、任务详情、AI 生成、提示词管理、审核中心、成果库、调用审计、成本统计、统计看板、模型管理、用户管理、操作日志、登录日志、个人中心和 403 页面。

前端通过统一 request 封装访问后端接口，并在请求中携带 token。路由守卫允许 `/login` 和 `/register` 未登录访问，其他后台页面需要登录；管理员页面通过路由 meta.roles 控制。前端界面采用后台管理布局，包括左侧菜单、顶部用户信息栏、表格、卡片、抽屉、弹窗、标签和统计图表。

## 三、系统测试与结果分析

### 3.1 测试环境

推荐测试环境为 Windows 10/11、Python 3.10+、Node.js 18+、MySQL 8.0、FastAPI、PyMySQL、Vue3 和 Vite。当前远程 Ubuntu/WSL 环境无法直接访问 Windows MySQL，且最终前端运行需要本地 Node 环境，因此数据库导入、前后端联调和截图需在本地 Windows MySQL + Node 环境补做。本报告不虚构远程完整运行结果。

### 3.2 数据库测试

## 四、实验结论与总结

### 4.1 实验完成情况

本实验完成了一个围绕 AI 项目协作质量审计场景的信息管理系统。数据库方面，系统设计了 27 张主业务表，并使用主键、外键、唯一约束、索引、软删除、审计字段、视图、触发器、存储过程、事务和乐观锁实现数据管理。后端方面，系统采用 FastAPI 分层架构和参数化 SQL，实现认证、项目、任务、输出、审核、成果、模型、统计和日志等接口。前端方面，系统基于 Vue3 后台模板二次开发，形成较完整的 Web 管理界面。文档方面，项目已整理 README、接口清单、测试素材、截图清单和最终检查清单。

### 4.2 实验心得

通过本次实验，我更加系统地理解了数据库应用系统从需求分析到实现测试的完整过程。数据库设计不只是建表，还需要从业务对象、关系、约束、索引、事务和审计角度整体考虑。尤其是在 AI 生成内容管理场景中，输出版本、审核记录、成果采用、模型调用和成本统计之间存在复杂关联，必须依靠清晰的数据模型保证可追溯性。

在实现过程中，我对事务、外键、唯一约束、视图、存储过程和乐观锁有了更直观的认识。多表写入如果缺少事务，很容易产生半成品数据；并发编辑如果没有 `lock_version`，就可能出现覆盖更新；统计查询如果没有合理索引和清晰表关系，后续展示和分析会变得困难。同时，前后端联调也让我认识到接口字段必须严格一致，例如 `title/task_type_id`、`keyword`、`failure_reason` 和 `save-as-new-version` 等字段和路径都需要在代码与文档中同步。

### 4.3 系统不足与改进方向

当前系统仍有进一步优化空间。第一，可以增加邮箱验证码注册、找回密码和更细粒度权限模型；第二，可以接入真实大模型 API，并对不同模型质量进行更丰富评估；第三，可以完善自动化测试和前端 E2E 测试；第四，可以增强统计看板图表和报告导出能力；第五，可以支持多租户、课程班级管理和部署上线；第六，需要在本地 Windows MySQL + Node 环境完成真实运行截图和完整联调验证。
